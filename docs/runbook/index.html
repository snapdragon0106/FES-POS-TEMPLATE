システムが止まっても、お店は止めない。
お金はいつも通り受け取り、売れたものは紙に書く。

会計を押したら、こう出た

「通信が途切れました…」

会計が記録されたかどうか分からない状態です。カートはそのままで、もう一度「会計を確定する」を押してください。 1回目がじつは記録されていた場合でも、二重には記録されません。システムが自動で見分けます。

これだけは注意 別のスマホで打ち直さない。ページを読み込み直してから打ち直さない。 二重防止が効くのは「同じ画面で、カートを変えずにもう一度押した」ときだけです。 どうしても別の端末で打つときは、先に履歴を見て記録されていないか確認します。

「会計完了！（先ほどの送信で記録済みでした）」

もう一度押したら、1回目がちゃんと記録されていたという意味です。正常です。そのまま次のお客様へ。

「サーバーでエラーが発生しました…」

システム側の問題です（多くはデータベース）。少し待ってもう一度押す。何度やってもダメなら管理者に伝えて、紙に切り替え。

紙に切り替えるとき（レジ係）

  1. お金はいつも通り受け取り、おつりもいつも通り渡す 合計は、商品の値段表を見て計算します。電卓があると安心です。

  3. 切り替えた時刻を管理者に伝える 「何時何分から紙です」。直前の会計がシステムに入ったかどうかの確認に使います。

紙の間は在庫の表示が合いません 紙で売った分はシステムの在庫から引かれていません。システム上で「残5」と出ていても、実物がもう無いことがあります。 紙の間は、実物の残りを見て判断してください。

「健康チェック」の読み方

システムの状態を確認するためのページです。合言葉を入れたことのある端末で開くと、次のような文字が出ます。 合言葉を入れていない端末（外部の人と同じ）では、中身を隠すため {"status":"ok"} か {"status":"unavailable"} だけが出ます。その場合はレジのスマホで開き直してください。

{"status":"ok","server":"ok","db":"ok","dbLatencyMs":45,"commit":"5285c6e","time":"..."}
項目意味
statusok なら全部正常。degraded なら一部が止まっている
dbデータベース（TiDB）につながるか。error ならDBの障害。starting は再起動直後
dbLatencyMsDBの応答時間（ミリ秒）。ふだんは数十〜数百。数千なら非常に遅い
commitいま動いているプログラムの版。修正を反映したとき、切り替わったかの確認に使う
帯とエラーの見分け レジの赤い帯は、端末が圏外なら「この端末が〜」、サーバーかDBの障害なら「サーバーに接続できません」と出ます。 DBが止まったときは、会計を押すと「サーバーでエラーが発生しました」と出ます。サーバー自体が止まったときは「通信が途切れました」です。

3種類別の直し方

どの場合も、直している間はレジ係に紙で営業してもらいます。

A. 1台だけおかしい（端末の問題）

  1. その端末で、電波・Wi-Fi・機内モードを確認する
  2. ページを読み込み直す（アプリなら一度閉じて開き直す）
  3. ダメならログアウトして、もう一度ログイン
  4. それでもダメなら、その端末は使わない。別の端末でログインすれば続けられる（データはすべてサーバー側にある）

B. 全台おかしいが、健康チェックは ok（会場ネットワーク）

  1. 会場のWi-Fiを切って、モバイルデータ（4G/5G）に切り替える
  2. 電波が弱い場所なら、テザリングできる端末を1台用意して、ほかの端末をつなぐ
  3. 時間帯によって混雑するなら、紙で営業して空いてから入力する

C. サーバーが止まっている（Render）

  1. まず1分待つ。無料プランのサーバーは、しばらく誰も使わないと休止し、次に開いたときの起動に30秒〜1分かかる（開店直後・休憩明けに起きやすい）。健康チェックのページを開いたまま待つ
  2. Renderのダッシュボード（dashboard.render.com）にログインし、サービスの状態と Logs を見る
  3. 直前に修正を反映していた場合 → ひとつ前のデプロイに戻す（Rollback）。これがいちばん確実
  4. そうでなければ、サービスを 再起動（Restart） する
  5. Render自体の障害（status.render.com）なら、復旧を待つしかない。紙で営業を続ける
再起動すると PINの入力ミスによるロックも解除されます。逆に言うと、ロックを解くためだけに営業中に再起動する必要はありません（自分のスマホなら5分で解け、ほかの人のミスで自分のスマホがロックされることはありません）。 ログアウトしたセッションは、再起動しても使えないままです（データベースに記録しているため）。

D. データベースが止まっている（TiDB Cloud）

  1. TiDB Cloudのコンソール（tidbcloud.com）にログインし、クラスタの状態を見る
  2. 無料枠（Request Units）を使い切っていないか確認する。使い切ると極端に遅くなったり止まったりする。支出上限（Spending Limit）を上げれば戻ることがある
  3. TiDB Cloud自体の障害なら復旧を待つ。DBが戻れば、サーバーの再起動なしで数秒で自動的に復帰する（事前に確認済み）

E. ログインできない

状況対応
「確認が完了しませんでした」と出る 入力欄の下の確認（Cloudflare）が済む前に送信した。確認の枠に「成功しました」が出てから、もう一度押す。 出ない・何度やってもだめなら、Wi-Fiを切ってモバイル回線で試す（会場のネットワークがCloudflareを止めていることがある）
「確認サービスにつながりませんでした」と出る サーバーからCloudflareに確認できていない（Cloudflare側の障害など）。ログイン済みのスマホはそのまま使える（確認はログインのときだけ）。 新しくログインする必要があるときは、確認を一時的に切る：Renderのダッシュボード → サービス → Environment で TURNSTILE_SITE_KEY と TURNSTILE_SECRET_KEY を2つとも消して保存（自動で再デプロイ、数分）。 片方だけ消すとサーバーが起動しない（旧版が動き続ける）。復旧したら同じ値を2つとも戻す
PINを5回まちがえた その番号でログインしたことのあるスマホなら、5分待てば解除される（ほかの人がその番号でミスしても、このスマホはロックされない）。
その番号で初めて使う端末からは、番号ごとに1時間に10回（管理者の番号は5回）、店全体で15分に30回までしか試せず、超えると最長1時間止まる（総当たり対策）。 いつもの自分のスマホで入る。急ぐならサーバーを再起動すると解ける（C）
管理者の画面に「PINの入力ミスが○回」と赤い帯が出た PIN管理 → 操作タブで、どの番号に・どの端末から・何時に間違えたかを見る。本人の打ち間違いでなければ誰かがPINを試している。 その番号のPINを管理者がリセットし、本人に新しいPINを伝える。合言葉が漏れていそうなら合言葉も変える（Renderの POS_ACCESS_CODE）
初めての人が「承認待ち」になる 本人の画面に出ている4文字の申請コードを見せてもらい、管理者がPIN管理の「承認待ち」にそのコードを入れて承認する。 コードが合わないときは、別の人が同じ番号で申請している。承認せず、本人にもう一度PINを設定してもらう（コードが新しくなる）
一般メンバーがPINを忘れた管理者がPIN管理でリセットする
管理者がPINを忘れた ほかの管理者がいればその人がPIN管理でリセットする。いなければ復旧コードで設定し直す（DBを直接触らない）:
  1. Renderのダッシュボード → サービス → Environment で POS_ADMIN_RECOVERY_CODE を追加する。 値は16文字以上のでたらめな文字列（パスワード生成などで作る。誰にも送らない）。保存すると自動で再デプロイ（数分）
  2. ログイン画面で管理者の番号を入れ、「管理者の復旧コードを使う」→ 復旧コードと新しいPINを入れる
  3. 入れたら、Renderから POS_ADMIN_RECOVERY_CODE を消す（消すまで、コードを知っている人は誰でも管理者のPINを変えられる）
復旧コードを5回まちがえると、1時間は使えなくなる。 以前の「TiDBで管理者の行を消す」方法は使わない：いまは消しても誰も承認できない承認待ちになるだけで、入れない
合言葉の画面で「試行回数が多すぎます」 誰かが合言葉を何度も間違えたため、初めて使う端末が10分止まっている。前に合言葉を入れたことのある端末は影響を受けない。10分待つ
管理者は1人だけ 取消・在庫補充・商品の変更・PINの承認は管理者しかできません。管理者がレジを離れている間にこれらが必要になったら、 メモしておいて、戻ってきたらまとめて処理します。 釣り銭の登録・締め・釣り銭の返却は、管理者のほかに会計係（管理者がPIN管理で指定）もできます。本部への回収と両替は誰でもできます。

F. データの問題

状況対応
間違えて会計した管理者が履歴から取消（削除ではなく取消）。売上も在庫も元に戻る
在庫の数が実物と合わない多いとき：管理者が商品画面で初期在庫を直す。少ないとき：在庫画面で補充
全データリセットを押してしまった「全データリセット」と入力しないと実行されない。実行してしまった場合はアプリの中では元に戻せない（操作ログも消え、誰がリセットしたかだけが新しいログの1行目とRenderのログに残る）。閉店ごとに保存したCSVと紙の記録から作り直す。営業が始まったらリセットは絶対に使わない

4紙での営業と、復旧後の入力

紙の分をあとから入力すれば、売上も在庫も正しくなります。

紙に切り替えると決めたら

  1. 全レジに「何時何分から紙」と伝える
  2. 各レジに記録用紙（付録）とペンを配る
  3. 値段表（商品と価格の一覧）をレジの前に貼る
  4. 受け渡しの画面にも注文が出なくなるので、レジ係が商品を直接渡すか、用紙の控えを受け渡し係に渡す
  5. 直す担当（管理者）と、売り続ける担当を分ける

直ったら（入力の手順）

  1. 全レジに「アプリに戻って」と伝え、用紙を回収する ここから先の新しい会計は、いつも通りアプリで。
  2. 切り替え直前の会計が入っているか、履歴で確認する 「通信が途切れました」のあと紙に書いた会計は、じつはシステムに入っていることがあります。時刻と中身が同じものが履歴にあれば、その行は入力しない。
  3. 1人・1台で、紙の行を順に入力する レジ画面で商品を入れて、預かり金は ちょうど。入力したら用紙の「入力済」に✓。複数人で分けると、同じ行を二重に打ちやすい。
  4. 入力が終わったら、受け渡し画面で「すべて渡した」を押す 紙の分の商品はもう渡してあるのに、入力した注文が「受け渡し待ち」に並ぶため。先にアプリで会計した分の受け渡しが終わってから押す。
  5. 最後に、レジの現金と「本日の売上」を照合する 合っていれば復旧完了。
入力するとどうなるか 売上の合計と在庫は正しくなります。ただし会計の時刻は入力した時刻になるので、売上画面の「時間帯別」のグラフだけは実際とずれます。合計金額には影響しません。

5事前の準備チェックリスト

障害のほとんどは、前日までの準備で防げるか、影響を小さくできます。

前日まで

  • アプリが最新の状態で動いている。健康チェックが "status":"ok" を返すことを確認した データベースの表や列はサーバーの起動時に自動で作られる。drizzle-kit push は実行しない（もし実行して「テーブルを空にしますか（truncate）」と聞かれたら、必ず No）
  • 本番で通し練習をした（スマホ2台以上で、同じ商品を同時に会計 → 在庫が正しく減る。取消もやってみる）
  • 全員が一度ログインしてPINを決め、管理者が申請コードを見て承認した。PIN管理画面に「未設定」「承認待ち」が残っていない 未設定の番号は、ほかの人が先に申請できてしまう（申請コードが本人の画面と合わなければ承認しないこと）。1234・0000のような推測されやすいPINは設定できない
  • 合言葉（Renderの POS_ACCESS_CODE）が、推測されにくく、クラスの外に漏れていない値になっている。変えるとログイン済みのスマホもみんな合言葉を入れ直すので、全員に新しい合言葉を伝えてから 去年の合言葉や、どこかに書いて貼り出した合言葉は使わない
  • 会計係を決めた（PIN管理の「会計係」）。釣り銭の登録・締め・返却を管理者以外がやる場合
  • Renderに POS_ADMIN_RECOVERY_CODE が残っていないことを確認した（管理者が最初のPINを決めるときと、PINを忘れたときだけ使うもの）
  • 商品・価格・原価・初期在庫・警告ラインを本番の内容にした
  • 練習で入れた取引を消した（商品タブの「練習を片付ける」） 「リセット」（全データリセット）は商品も消えるので、使った場合は商品を入れ直す
  • TiDB Cloudで、無料枠（Request Units）の残りと支出上限を確認した。バックアップ機能が使えるかも確認した
  • Renderのプラン（無料か有料か）を確認した。Render・TiDB Cloudにログインできる人を2人以上決めた
  • この手順書を印刷し、管理者とリーダーのスマホにも保存した
  • 紙の売上記録用紙を各レジ5枚印刷した。ペン・電卓・値段表を用意した
  • 付録の緊急連絡先を埋めた
  • Androidの人はアプリ、iPhoneの人はホーム画面への追加を済ませた。モバイルバッテリーを用意した
  • ログインの確認（Cloudflare Turnstile）を入れている場合：会場のWi-Fiで、Androidアプリ・iPhone・PCのそれぞれから合言葉とPINを通してみた 通らないときの対応は3章E。全員が前日までにログインしておけば、当日にCloudflareが止まっても影響しない

当日の朝（開店15分前）

  • 管理者が健康チェックを開く（休止中のサーバーを起こす＋状態の確認）
  • 全レジでログインし、画面の上に赤い帯が出ていないことを確認
  • 1台で試しに1件会計 → 管理者が取消（本番で動くことの確認）
  • 会場のWi-Fiとモバイルデータ、両方つながることを確認
  • 2日目の朝は、全員ログインし直す（ログインは24時間で切れる）

閉店後

  • 売上画面から取引明細のCSVをダウンロードして保存（その日のバックアップ）
  • レジの現金と「本日の売上」が合っているか照合
  • 紙で営業した時間があれば、入力漏れがないか用紙の「入力済」を確認

6当日は修正を反映しない

営業中に main に push すると、その瞬間に本番が切り替わります。

RenderはGitHubの main ブランチに push されると、自動で本番に反映（デプロイ）します。営業中にこれが起きると:

  • 数十秒〜数分、サーバーが不安定になる
  • 開いている端末が新しい版を読み込み直すことがあり、作りかけのカートが消える
  • 修正に不具合があれば、その場で全レジが止まる

営業日は main に push しない（凍結）。見つけた不具合は、閉店後か翌日の開店前に直します。

どうしても営業中に直す必要があるとき

  1. お客様が途切れたタイミングを選び、全レジに「1〜2分止まります」と伝える（その間は紙）
  2. push して、Renderのダッシュボードでデプロイが終わるのを待つ
  3. 健康チェックの commit が新しい版に変わったことを確認
  4. 全レジでページを読み込み直してもらう
  5. おかしければ、すぐにRenderでひとつ前のデプロイに戻す（Rollback）
